# Project profile

## About

- What this repository is: `grpc-server-kit`, a Python library for building async gRPC servers on `grpc.aio`, published on PyPI. It covers the app facade, the builder, TLS, lifecycle, health checking, streaming-aware interceptors and observability.
- Who uses it: services that run a `grpc.aio` server.
- Language, version and main frameworks: Python 3.12 and newer. The only runtime dependency is `grpcio`. Optional extras: `reflection`, `channelz`, `settings` (Pydantic), `health`, `postgres` (SQLAlchemy), `redis`, `metrics` (Prometheus), `tracing` (OpenTelemetry), `sentry`, `dishka` (Dishka DI) and `all`.
- Where the documentation lives: https://bedrock-python.github.io/grpc-server-kit/, built with Zensical from `docs/` (`zensical.toml`). The API reference is generated from docstrings. `docs/agents.md` is the one-page reference for coding assistants.

## Commands

| Task | Command |
|---|---|
| Install dependencies | `make install`: `uv sync --group dev --all-extras`, as CI does. Without `--all-extras`, `mypy` cannot load the `pydantic.mypy` plugin and 13 test modules fail at collection. |
| Format | `make fmt`: `uv run ruff format .`, then `uv run ruff check --fix .` |
| Lint and type-check | `make check`: `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy grpc_server_kit` |
| Test | `make test-unit` (`uv run pytest -m unit`) and `make test-integration` (`uv run pytest -m integration`). `make test` runs both with `--cov-fail-under=90`. CI runs `uv run pytest -m unit --cov=grpc_server_kit --cov-report=xml --cov-fail-under=90` on Python 3.12, 3.13 and 3.14, and runs `uv run pytest -m integration` in a separate job. |
| Run locally | A library: nothing to run. Each script in `examples/` starts a server and exits on its own, for example `uv run python examples/minimal_server.py`. The docs: `make docs-serve`. |
| Stop the local run | Ctrl+C in the terminal of `make docs-serve`. The examples stop by themselves. |

## Conventions

- Default branch: `master`. A ruleset only lets it change through a pull request with the `All checks passed` check. The pre-commit hook `no-commit-to-branch` also refuses local commits to it.
- Issue tracker: GitHub Issues of this repository. Refer to an issue as `#123`.
- Branch names: `<type>/<short-description>`, such as `feat/my-feature` (CONTRIBUTING.md).
- Commit messages: Conventional Commits, enforced by the `conventional-pre-commit` hook (`uv run pre-commit install --hook-type pre-commit --hook-type commit-msg` installs every hook; CONTRIBUTING.md installs only the commit-message one, so ruff does not run at commit time). A breaking change takes `!` or a `BREAKING CHANGE:` footer. Pull requests are squash-merged and release-please reads the squash title, so the pull request title must be a Conventional Commit too. For a one-commit pull request, GitHub uses the commit's title instead. Only `feat`, `fix`, `perf` and `revert` appear in the changelog.
- Language of pull request titles and descriptions: English.
- Where specs and design notes go: in the pull request description. The repository has no place for them.

## Boundaries

- `CHANGELOG.md` is generated by release-please. Never edit it by hand, and never add an `## [Unreleased]` section. `docs/changelog.md` is an untracked copy that the docs build makes.
- The version lives in two places: `grpc_server_kit/__version__.py`, on the line marked `# x-release-please-version`, and `.release-please-manifest.json`. release-please bumps both. Never change them by hand.
- `docs/agents.md` is part of the public API. It changes in the same pull request as the API, and each new docs page adds a row to its documentation map (CONTRIBUTING.md, "The agents page").
- Some files come from the engineering-assets hub (`AGENTS.md` explains how it works):
  - the copy-page files: `docs/assets/javascripts/copy-page.js`, `docs/assets/stylesheets/copy-page.css`, `overrides/main.html`, `scripts/emit_markdown.py`;
  - `.github/workflows/docs.yml`, `.github/workflows/release-please.yml` and `.github/dependabot.yml`;
  - `.editorconfig` and `CODE_OF_CONDUCT.md`.

  Change them in the hub. A change made here makes the file this repository's own.
- Never publish to PyPI or create a release by hand. release-please creates the release, and `publish.yml` publishes it.

## Notes

- Releases: release-please opens its pull request with the workflow's own token, so CI does not start on it and the required `All checks passed` check never reports. Close and reopen the release pull request to run CI, then merge it. When the Release Please run completes, `publish.yml` publishes the `grpc-server-kit-vX.Y.Z` tag to PyPI. Before 1.0, a breaking change bumps the minor version.
- Tests: every test carries the marker `unit` or `integration` (`--strict-markers`). `tests/conftest.py` sets the marker by directory, and each module also declares `pytestmark`. The tests in `tests/integration/` start a real `grpc.aio` server in the same process on `127.0.0.1`. They need no Docker.
- Test style (CONTRIBUTING.md):
  - one behaviour per test;
  - Arrange, Act, Assert, in that order;
  - names follow `test__subject__condition__expectedresult`;
  - `pytest.mark.parametrize` instead of near-identical tests, with `pytest_lazy_fixtures.lf()` to pass fixtures;
  - `conftest.py` only for fixtures shared across modules.
- Code style (CONTRIBUTING.md): type hints on every function, tests included; Google-style docstrings on the public API only; lines up to 120 characters; double quotes; comments only for a non-obvious why.
- Layout (README.md, "What's inside"): async code lives in `grpc_server_kit/aio/`, mirroring `grpc.aio`. Modules used by both sync and async code stay at the top level. `grpc_server_kit` and `grpc_server_kit.aio` must import with `grpcio` alone. Code there that needs an extra imports it inside `try`/`except ImportError`, and raises an `ImportError` naming the extra when someone uses the feature.
